# Security Policy

## Data boundary

Dian Agent reads visible data from pages the user is already signed in to. It does not read browser cookies and sends snapshots only to `127.0.0.1` by default.

Never commit files under `bridge/data/`, generated reports, browser profiles, extension signing keys, or exported shop data. These paths are excluded by `.gitignore`.

Feishu and DingTalk robot Webhooks are secrets. They are accepted only for the official HTTPS hosts, redirects are rejected, and the local service never returns them in full. Complete URLs are protected for the current OS user by Windows DPAPI or the macOS login Keychain; the protected record is bound to the local install ID, and the macOS service/account namespace also includes a normalized-install-root fingerprint so two installations do not share a destination. `integrations.json` contains only schema/revision data, connection flags and one-way destination fingerprints. A legacy plaintext file is migrated on first read or write only after the protected record has been written and read back successfully. A legacy unscoped Keychain item is accepted only when its random revision matches this installation's local metadata, then copied into the scoped item. If the native secret store is unavailable, notification reads, tests and sends fail closed; the one remaining legacy plaintext copy is retained for a later migration retry instead of silently losing the user's connection. Migration cannot erase copies already retained by backups, filesystem snapshots or storage remanence. DPAPI and login Keychain protect secrets at rest but do not defend against a malicious process already running as the same unlocked OS user; the Agent necessarily materializes a Webhook in memory while sending it. Do not paste a real Webhook into an issue, screenshot, test fixture, or committed configuration file. If a Webhook is exposed, delete or rotate the robot immediately in the corresponding group settings.

## Local API boundary

The browser extension must be pre-authorized by its extension ID and exchange that identity for a short-lived signed session. Sessions bind a schema version, audience, subject, nonce, issue time, expiry and the running extension version. Extension sessions require the matching browser Origin. Without a valid internal-maintenance session, an Origin-less client is limited to the sanitized health and activation contracts; a formally provisioned internal-maintenance subject may receive the redacted `/system/status` summary but cannot reuse an extension session.

Business reads and all writes require a valid session. Store, advertising-account, plan, task and readback operations carry their original scope and fail closed on conflicts. High-side-effect POST requests use a bounded 30-second in-process idempotency window so a browser retry cannot immediately submit the same operation twice. This window does not survive an Agent restart and is not a substitute for a durable platform idempotency key on a future production funds path.

The localhost boundary protects against an unrelated web page and accidental cross-store reuse. It does not authenticate any native process that can reach this machine's loopback port, including a process running as another local OS user where the host permits that access. The current release therefore assumes one trusted desktop user and a non-hostile local process boundary. Multi-user or adversarial-host deployment requires Native Messaging, an OS-user-bound IPC channel, or an equivalent one-time paired transport before production write authority can be enabled.

## Network and update boundary

OAuth, official data API and Webhook requests reject redirects so credentials are not forwarded to another destination. Knowledge-pack downloads require HTTPS and revalidate the effective URL. Offline-upgrade health checks accept only loopback HTTP and reject redirects; self-tests use isolated temporary data and log directories rather than the live store database.

Windows and macOS installers stage and validate complete Agent, extension and maintenance-tool trees before activation. Installation, repair, offline update, removal and watchdog maintenance share an installation-root lock. The packaged Agent reports its own version before files are copied; that receipt must match both extension manifests and the target version. Activation uses a durable cross-tree transaction, atomic directory replacement and reverse-order recovery across the runtime, extension, tools, version pointer and startup registration. On Windows, the scheduled task and Startup shortcut execute a recovery bootstrap and policy stored outside every switched tree; it remains available through both tools rename windows. The separate release-tools journal binds its transaction ID to exact direct-child stage and backup paths, and all maintenance entrypoints recover or refuse unresolved journals before mutation. Recursive symlinks, junctions, reparse output paths and unsafe archive paths are rejected. The macOS build command runs its Darwin/launchd recovery matrix before producing an artifact, and the first distributable build must retain the complete Apple Silicon result as release evidence. Runtime and build dependencies are pinned, and the v4.14.0 dependency sets are checked with `pip-audit` before packaging.

## Reporting a vulnerability

Please open a GitHub security advisory for vulnerabilities involving data exposure, permission scope, local bridge access, or unsafe browser actions. Avoid including real shop, customer, order, account, or advertising data in reports.

## Execution boundary

The supervised executor is limited to one classic-Qianchuan plan at a time and only supports a budget reduction, restoration to the exact previously verified budget, or pausing a plan whose current running state was freshly verified. It requires a fresh page reread, an exact final confirmation phrase, a 60-second single-use grant, a unique store, account and plan match, and an operation-specific verified current value. A budget reduction may not exceed 30%. It submits only when exactly one supported platform control and confirmation button are present, records the platform receipt, then rereads the page to verify the target value. The legacy single-plan executor is disabled in Chengfang mode.

The private commercial Chengfang adapter has a separate production boundary. It can update only one parent-plan budget through the official Ocean Engine API, and the authorized target must be lower than two consecutive official detail reads and no more than 20% below the bound snapshot value. Every operation is bound to an opaque parent-plan key and snapshot fingerprint, uses an exact confirmation phrase and short single-use grant, persists the executing state before network I/O, and performs an official GET readback after the single POST. There is no browser DOM write fallback. Any ambiguous response, missing readback or crash after authorization enters a durable unknown state; unknown/executing work freezes all other Chengfang production writes until official read-only reconciliation completes. A persistent production kill switch cancels prepared/authorized work and blocks prepare, authorize and execute on the server.

The official absolute-budget update endpoint does not expose a compare-and-swap version or conditional old-value parameter. Consecutive preflight reads narrow but cannot mathematically eliminate an external actor changing the same plan in the final read-to-write interval. The UI must disclose this residual concurrency risk, operators must avoid concurrent edits to the selected parent plan, and a response must never be described as “unchanged” or “not written” solely from an HTTP/platform error after POST was attempted. No automatic retry or compensating increase is allowed.

Unverified budget increases, bulk changes, plan resume, bids, inventory, orders, refunds and account funds remain disabled. A missing or ambiguous selector, store, account, plan, current value, control, button or success receipt stops the executor rather than guessing or retrying.

The only supported increase is a rollback to the exact pre-execution budget from a verified reduction record. It requires a fresh page value equal to the prior reduced target and follows the same confirmation, single-use authorization, submit receipt and postflight verification flow.

Budget drafts are blocked unless they bind a selected account, a platform plan ID, a fresh high-quality snapshot, a readable current value, and a policy-compliant target value. A missing budget must never fall back to a pause action.
